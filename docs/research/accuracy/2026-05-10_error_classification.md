## 카테고리별 분류

### Category 1: 사전 미등록 (UNKNOWN으로 처리됨)
**0건**

평가 데이터셋에 사전 미등록 단어가 없음. 모든 단어가 mecab-ko-dic full dict에
등록되어 있음. → 이 데이터셋에서는 "사전 확장"이 정확도 개선 수단이 되지 못함.

### Category 2: POS 오류 (분절은 맞고 태그만 틀림)
**3건 / 4건 (75%)**

| 케이스 | 형태 | 예상 POS | 결과 POS |
|--------|------|----------|----------|
| 크리에이터 되고 싶어 | 되 | VV (본동사) | XSV (동사파생접미사) |
| 보지만 하지만 | 보 | VV (동사) | NNG (일반명사) |
| MBTI가 뭐예요 | MBTI | SL (외국어) | NNP (고유명사) |

**공통 특성**: 동일 표면형이 여러 POS로 분석 가능 (다의어).
- `되`: VV(되다, 본동사) / XSV(공부되다처럼 파생) / NNB(되, 의존명사)
- `보`: VV(보다) / NNG(보, 한자어 명사) / XPN(접두사)
- 영문 약어: SL(외국어) / NNP(고유명사) — 사전 등록 정책 차이

**원인**: Viterbi 경로 선택 시 컨텍스트가 부족하여 wrong POS의 비용이 더 낮음.
- `되` 단독 비용은 XSV가 VV보다 낮을 수 있음 (XSV가 더 흔함)
- `MBTI`가 사전에 NNP로 등록되어 있고 SL 매핑 규칙 부재

### Category 3: 분절 오류 (경계가 다름)
**1건 / 4건 (25%) — 부분적**

`MBTI가 뭐예요` 케이스에서 `가` 처리:
- 예상: `가/JKS` (주격조사)
- 결과: `가/VV 아/EF` (Inflect 분해)

원본 MeCab이 `가/VV+EC`(Inflect 표기)로 분석한 것을 평가 코드가
세종 형식으로 변환할 때 `가/VV + 아/EC`로 풀어버림.
실제 정답은 `가/JKS`이지만 분해 후 정답이 다른 길이가 되어 분절 불일치 발생.

**원인**: Inflect 토큰 처리 로직과 정답 변환 로직의 불일치.

### Category 4: 공백 처리 오류
**0건**

Sprint 118의 Viterbi OOB 수정 후 공백 경계 처리는 정상.

### Category 5: 융합 토큰 분해 오류
**보조 분석에서 다수 발견 (모두 정답으로 일치)**

`test_xsv_debug_sentences`에서 MeCab 원본의 융합 토큰이
세종 형식으로 올바르게 분해되는 경우들:

| MeCab 원본 | 세종 변환 (정답) | 결과 |
|------------|------------------|------|
| `하면서/XSV+EC` | `하/XSV 면서/EC` | ✓ |
| `됐다/XSV+EP+EF` | `되/XSV 었/EP 다/EF` | ✓ |
| `결과가/NNG+JKS` | `결과/NNG 가/JKS` | ✓ |
| `보이다/VV+VX+EF` | `보/VV 이/VX 다/EF` | ✓ |

대부분의 융합 토큰은 정상 분해. 단 위 Category 3의 "Inflect 메타데이터 처리"는
별도 문제로 남아 있음.

## Top Error Patterns

빈도순 정렬 (실패 4건 기준이므로 통계적 의미는 제한적):

1. **VV ↔ XSV 모호성** (1건): "되" 본동사 vs 파생접미사
2. **VV ↔ NNG 모호성** (1건): "보" 본동사 vs 명사
3. **SL ↔ NNP 모호성** (1건): 외국어 약어 분류
4. **Inflect 분해 vs 조사 분석** (1건): "가" VV+EC vs JKS

## 사전 확장이 해결하지 못하는 이유

전통적으로 형태소 분석 정확도 개선은 두 가지 축이 있음:

| 축 | 효과적인 경우 | 본 baseline에서 |
|----|--------------|----------------|
| 사전 확장 | UNKNOWN 빈발 시 | **해당 없음** (UNKNOWN 0건) |
| 비용/연접 학습 | 모호성 해소 필요 시 | **해당함** (4건 모두 모호성) |

→ DIC-005(신조어 수집), DIC-006(IT 용어) 같은 사전 확장 작업은 본 데이터셋의
99.9%를 100%로 올리는 데 기여하지 못함. 더 noisy/diverse한 데이터셋에서만
유의미.

## Sprint 122 권고 방향

baseline 분석 결과, 다음 방향이 ROI가 높음:

### 우선순위 1: 평가 데이터셋 확장
- 99.9%는 너무 높아 추가 개선 신호가 약함
- 세종 코퍼스 또는 noisy real-world 데이터(SNS, 신조어 포함) 통합 필요
- 그래야 진짜 약점이 드러남

### 우선순위 2: C++ mecab-ko 일치율 측정
- drop-in replacement 검증
- mecab 바이너리 설치 + 비교 스크립트
- 99.9% baseline이 C++ 원본과 동일한지 확인

### 우선순위 3 (보류 가능): 모호성 해소 4건 디버그
- 개별 케이스에 대한 회귀 테스트 추가
- 단, 현재 Viterbi 비용 구조는 baseline에 최적화되어 있어
  4건을 고치면 다른 케이스가 깨질 수 있음 → 신중

## 학습 포인트

### 1. "측정 없는 개선"의 위험
Sprint 117까지 mini-dict 100%를 보고 만족했지만, full dict 측정 한 번이
프로젝트의 진짜 상태(99.9%, 매우 양호)를 드러냄.
**개선보다 측정이 먼저**여야 함.

### 2. 데이터셋의 한계 인지
99.9%는 "이 데이터셋이 너무 쉽다"는 신호일 수 있음.
정확도가 높을수록 데이터셋의 다양성/난이도가 의심되어야 함.

### 3. 사전 vs 모호성 해소의 구분
미등록어 vs 다의어는 완전히 다른 문제.
실패 케이스를 카테고리화하지 않으면 잘못된 해결책(사전 확장)으로 시간 낭비 가능.
